# Первый промпт для Codex — реальный визуальный редактор, НЕ ещё одна заготовка

Работаем в **существующем репозитории** `messagetomedium/TIMELINE`, ветка `main` (текущая база: коммит `35afb255d4a6cd0c329122ecb201fba71c20cc22`). Создай новую рабочую ветку `feat/visual-timeline-v2` и сделай настоящий первый вертикальный срез редактора. НЕ создавай новый репозиторий, НЕ меняй весь стек и НЕ реализуй сейчас Supabase, авторизацию, ChatGPT или сервер.

**Сначала прочитай файлы из комплекта `00_START_HERE.md`, `01_PRODUCT_AND_UX_SPEC.md`, `02_ARCHITECTURE.md`, `03_CODEX_EXECUTION_PLAN.md` и текущий код.** Эти файлы имеют приоритет перед старыми `ARCHITECTURE.md` и `CODEX_SPEC.md`, когда формулировки конфликтуют. Не выполняй только «нулевой каркас», он уже есть.

## Почему это новое задание

Сейчас приложение показывает пустой экран проектов, кнопку демо и затем текстовую сводку. Это не то, что заказано. Требуется визуальная рабочая область по логике PDF-референса: **горизонтальная календарная шкала, цветные процессы с задачами, этапы в виде вертикальных границ, исполнители снизу на общей оси, правая панель и инструменты почти как в Figma**. Визуальный редактор должен появиться в браузере в этой итерации. Запрещено снова отчитаться только типами и архитектурой.

## Что реализовать СЕЙЧАС (V1, приоритетная видимая вертикаль)

1. Заменить `ProjectSummary` как основной экран проекта на `TimelineWorkspace`, занимающий всю доступную ширину и высоту браузера. Убрать ограничивающую редактор ширину `main` из текущего CSS. На первом открытии показывать редактируемый насыщенный демо-проект с таймлайном (без отдельного клика «Показать демо»). Список проектов оставить доступным из верхнего меню. Для V1 допустим in-memory демо; **не притворяться, что данные уже сохраняются**.

2. Сделать **реальную горизонтальную шкалу дат**: сверху заголовки дней/недель/месяцев, ниже прозрачная вертикальная сетка. Выбрать непрерывные календарные интервалы, не считать месяц 30 днями. Одна функция date→x и обратная x→date используется для ВСЕХ элементов. Вверх/низ у сцены могут быть разные слои, но горизонтальное выравнивание не должно расходиться.

3. Нарисовать demo: минимум 4 визуальных этапа (например Подготовка, Препродакшн, Продакшн, Постпродакшн), 8 процессов, 25 задач с разумными длительностями и реальным параллелизмом/последовательностью, плюс 1–2 лида и несколько художников/других исполнителей. Это не вертикальный список карточек: полосы должны реально занимать разную ширину согласно датам. Сцена должна быть плотной, но читаемой и напоминающей предоставленный PDF.

4. **Этапы**: верхняя полоса названий и дат, вертикальные тонкие линии границ, круглая ручка наверху. При переносе круглого маркера дата меняется, а подпись обновляется. Это НЕ папки/родители задач.

5. **Процессы** — цветные горизонтальные плашки-контейнеры, внутри них дочерние задачи. По одиночному клику процесс выделяется, справа открывается информация и его вложенные task lanes раскрываются вниз. Соседние процессы тоже можно раскрыть, предыдущие не закрываются. На полосе только название процесса. Задачи на разных строках означают параллельную работу; последовательные задачи на одной строке справа друг от друга. Программно случайно не переставлять строки.

6. **Нижний блок исполнителей**: горизонтальные полосы занятости на тех же календарных датах, что и задачи, в визуально отдельной секции снизу. Достаточно read-only назначений в этом V1, но наличие блока и **подсветка исполнителя при наведении на задачу** обязательны. При zoom/pan нижний и верхний блок должны остаться синхронными.

7. **Правая панель**: по клику на процесс/задачу отображать название, даты, статус, описание, исполнителя (пока можно только read-only часть); отобразить цвет процесса. На V1 минимум одно живое редактируемое поле (название), которое обновляет плашку. Не делать отдельную страницу сводки.

8. **Нижняя плавающая панель**: реально работающие кнопки `+`/`−` масштаба, выбор шага сетки (`1 день`, `2 дня`, `3 дня`, `неделя`, `2 недели`, `месяц`) и кнопка подсветки выходных. Zoom и шаг сетки не связаны друг с другом. Подсветка суббот/воскресений бледно-зелёная. Добавить отдельную линию **сегодняшнего дня**.

9. **Навигация**: перемещение сцены средней кнопкой мыши при удержании, а также зажатой ЛКМ на пустом фоне; при pan ничего не изменяется в данных и не сдвигаются отдельные блоки. Zoom сохраняет календарное положение логически.

10. **Базовые жесты редактирования, не просто нарисованные ручки**:
    - двойной клик на названии полосы → inline-редактирование текста с Enter/Esc;
    - маленькая отдельная ручка сверху-слева полосы → drag по календарю, с реальным изменением дат;
    - левый и правый край → изменение длительности;
    - перенос процесса → его задачи сдвигаются с ним на то же количество календарных дней, без двойного переноса;
    - растягивание задачи наружу → граница процесса автоматически расширяется;
    - простой визуальный preview во время жеста и commit на pointerup, отмена жеста по Esc.

11. Приоритет V1 — **достоверная компоновка и работающие действия**. Сложные множественные выделения, Undo/Redo, библиотека людей, IndexedDB, портфолио и PDF — следующие этапы из плана, не нужно начинать их вместо выполнения V1. Если времени или объёма задачи недостаточно, закончи сначала настоящий календарь, полосы, раскрытие и навигацию, затем базовые drag/resize; честно укажи неполное. Не заменяй неготовые функции декоративными кнопками.

## Технические ограничения

- Переиспользуй существующий Vite/React/TypeScript/Zod, календарные функции и тестовую конфигурацию.
- React-компоненты рендерят data-driven данные по датам, а не hardcoded CSS-позиции, не готовую картинку PDF и не таблицу.
- Общий `TimelineCamera` и единые функции `xForDate`, `dateAtX`, `snapDate`. Независимые `pxPerDay` и `snapStep`.
- Для полос допустим DOM с absolute position, для сетки SVG; рендер должен поддерживать раскрытые процессы с увеличением высоты строк. Можно добавить Zustand позже, не вводить пустую архитектурную сложность.
- Один drag начинается только при нажатии на явную ручку; текст плашки не является drag handle; края — resize targets. Используй Pointer Events и обрабатывай pointercancel.
- Никакой многопользовательской логики, регистрации, AI, fake синхронизации, процента прогресса или неизменяемых экранов «планируется» на месте редактора.

## Что считаем выполнением и что показать в отчёте

1. Реальный скриншот загруженного `TimelineWorkspace` минимум в размере 1440×900; он должен содержать: **даты сверху, названия этапов, цветные процессы разной длины, задачи на строках, исполнителей снизу и правый инспектор**. Сохранить скриншот в репозитории `docs/screenshots/timeline-v2-first.png` (если позволяет среда) и указать ссылку/путь.
2. Проверить в браузере два одновременно раскрытых процесса; pan/zoom не разъединяют x-позиции задачи и исполнителя; изменение шагов сетки не меняет реальные даты; `Выходные` переключают фон.
3. Проверить мышью как минимум: двойной клик и изменение названия, отдельный drag-handle процесса, resize задачи, перенос этапной линии и выбор элемента с правой панелью.
4. Добавить Playwright сценарии на видимость реальных элементов и минимум пару жестов. Выполнить `npm run lint`, `npm run build`, `npm run test`, `npm run test:e2e`; указать фактические результаты и невозможные проверки честно.
5. В конце перечислить изменённые файлы, дать точные инструкции запуска, URL опубликованной версии **только если публикация действительно подтверждена**, и отдельно перечислить, что осталось для V2.

**Критерий отказа:** если после коммита интерфейс всё ещё состоит из обзора проектов и текстовой сводки без редактируемой временной сцены, задание НЕ ВЫПОЛНЕНО. Не завершай работу отчётом о чистой архитектуре вместо браузерной проверки.
