# TIMELINE — ТЗ на следующую доработку: V1.1 «Календарь прежде всего»

**Исполнитель:** Codex. **Репозиторий:** `messagetomedium/TIMELINE`, продолжение существующего кода `main`. **Версия требований:** 29.10.2026.

## 0. Задача и критерий результата

Сейчас редактор функционально похож на миниатюрный годовой обзор. Нужен визуально считываемый **интерактивный календарь производства**: месяцы → чёткие деления недели/дня → сквозные вертикальные границы → задачи и занятость, строго совмещённые по датам. Как в референсе PDF: большая горизонтальная временная композиция, сверху задачи, снизу занятость, а не вертикальный список дел.

В этой итерации отладить **визуальный редактор и навигацию**, а не реализовывать с нуля новый продукт. Код уже умеет drag/resize/разворачивание. Это должно сохраниться.

**Критерий отказа:** приложение по-прежнему по умолчанию ужимает год в один экран, недельные столбцы нечитаемы и нельзя сразу соотнести полосы с отчётливыми колонками дат — задача не выполнена независимо от числа тестов и переписанных компонентов.

## 1. Первый экран и масштаб по умолчанию

1. Убрать автоматическое правило `pxPerDay = (viewportWidth - 200) / totalProjectDays` из `ResizeObserver` в `TimelineWorkspace.tsx`. Оно оправдано только для отдельной команды «Весь проект», но не как стартовый вид.
2. Открывать проект в **рабочем масштабе**, например около 12–16 CSS px на календарный день при desktop 1440×900; окончательно подобрать по визуальной проверке. Цель: на доступной временной части рабочего поля видно примерно 6–12 недель, а не сразу весь год. Минимальная ширина недельного столбца в стартовом виде — 75 px.
3. Первичная точка просмотра: если сегодня попадает в диапазон проекта, расположить сегодняшнюю дату примерно в первой трети видимой оси; иначе показать начало ближайших актуальных работ/начало проекта. Не терять более ранние даты: доступны панорамой и кнопкой «Весь проект».
4. Добавить отдельные работающие команды в нижнюю панель: **Сегодня** (центровать/привести сегодня в видимую область) и **Весь проект** (один раз уместить расписание в поле). Эти команды меняют камеру/масштаб, а не данные задач или привязку.
5. Не ресетить zoom и pan при простом изменении размера окна. Для явного `Весь проект` брать ширину измеренного **временного viewport**, не ширину всей страницы и не ширину инспектора.
6. В стартовом демо сохранить несколько раскрытых процессов и нижнюю зону исполнителей; на экране сразу есть осмысленные цветные работы на разных датах.

## 2. Действительно календарная шапка

Сделать читаемый **двухуровневый календарный заголовок**, связанный с той же камерой:

- Первая строка: месяцы и годы, с визуальными границами каждого настоящего календарного месяца: «Октябрь 2026», «Ноябрь 2026» и т. п. Длина месяца — фактические 28/29/30/31 день, никакой одинаковой ширины месяцев.
- Вторая строка: **ячейки выбранного шага** (1, 2, 3 дня; 1, 2 недели; месяц), а не редкие числа, нарисованные поверх произвольного фона.
- Для `1 день` метка «29» и, если достаточно места, краткий день недели «чт»; для 2/3 дней — читаемый диапазон («29–30» / «29–31»); неделя — диапазон «26 окт — 1 ноя» или сокращённый вариант в узком столбце; 2 недели — диапазон; месяц — название месяца.
- Видимые даты на шкале вычисляются из календаря, а не из индекса элемента. Недели начинаются в понедельник; 2-недельный шаг остаётся последовательным с единой точкой привязки.
- При сильном отдалении не накладывать 10–20 текстовых меток друг на друга: пропускать только текст, когда не хватает пространства, но не искажать ширину календарных интервалов. При этом пользователь может видеть выбранный шаг в панели инструментов.
- Убрать статический заголовок `2026 — 2027`; динамически показывать правильные годы видимого диапазона.
- По визуальной иерархии календарная шапка должна быть одним из главных элементов интерфейса, а не слабым мелким текстом.

## 3. Общая календарная сетка

1. Столбцы выбранного шага должны быть видны в основном поле сквозными **полупрозрачными вертикальными границами**, согласованными с шапкой.
2. Те же X-координаты обязательно проходят через этапы, процессы/задачи и нижнюю занятость. Отступ левой фиксированной секции учесть **один раз**, без отдельной подгонки для каждого слоя.
3. Степень выраженности: границы месяцев чуть сильнее границ недель/дней; светлый спокойный фон. Разделители строк значительно слабее календарных вертикалей. Никакого цветного «расписания-шахматки».
4. Переключатель «Выходные»: субботы/воскресенья обозначаются бледно-зелёным вертикальным фоном ровно на соответствующие даты, одновременно в верхнем и нижнем блоке. При отключении подсветка исчезает; рабочие даты не меняются.
5. Разделители этапов с круглой ручкой и линия «Сегодня» — **отдельные** более различимые сквозные маркеры. Сегодня показывается только в своей правильной календарной точке; не приклеивать линию к окну.
6. Шаг сетки/привязки и масштаб по-прежнему **независимы**: выбор `1 день` не обязан автоматически приближать, а кнопка `+` не должна изменять `1 неделю` на другой шаг.
7. При маленьком zoom допустимо скрывать часть подписей для предотвращения наложений, но snapping должен оставаться на выбранных пользователем календарных границах.

## 4. Геометрия, фиксированные подписи и панорамирование

- Временная область — одна логическая координатная система `date -> X / X -> date` для шапки, StageBand, полос, performers и экспорта в будущем. Сохранить переиспользование `xForDate`, `dateAtX`, `widthForInterval`, `snapDate`, `zoomCamera`; при необходимости только дополнить их.
- Создать настоящую **фиксированную левую область заголовков секций** («Этапы», «Процессы», «Исполнители»), например 150–190 px, которая не движется горизонтально с датами и не маскирует полосы. Не имитировать её непрозрачным градиентом поверх сцены без корректной геометрии. Если вводится отдельный временной viewport, все `PointerEvent` и cameraX должны использовать его реальную ширину.
- Горизонтальный pan средней кнопкой мыши/ЛКМ на пустом поле двигает дату во всех секциях синхронно. Вертикальный scroll основного блока не должен сдвигать календарную шапку по Y.
- Zoom `+/-` привязан к центру **временной** видимой области (не всей страницы вместе с правой панелью), сохраняет календарную точку под центром; изменения расписания не выполняет.
- Подписи баров остаются **только названиями**, даты считываются из календаря и правой панели. Не превращать блоки в карточки с датами, аватарами, прогрессом или мини-таблицами.
- Сохранить плотность: процессы и задачи располагаются на вручную заданных дорожках, последовательные рядом на одной строке, параллельные друг над другом; никакой рандомной или автоматической «красивой» раскладки.

## 5. Этапы и даты

- Этап остаётся **вертикальным визуальным разделителем**, не родительской сущностью задачи. Его можно передвинуть за круглый маркер — дата пересчитывается; нельзя пересечь соседнюю границу без явного допустимого изменения модели.
- Добавить прямой ввод даты границы этапа (через компактный popover/инспектор по клику маркера; ISO хранится, русская дата отображается): изменение даты двигает маркер и линию. Это было отдельно согласовано в брифе и отсутствует сейчас.
- Подпись этапа и интервал его границ должны оставаться различимыми в рабочем масштабе; вид не обязан раскрывать всё производство одновременно.

## 6. Что необходимо сохранить из работающего V1

- Единые точные календарные даты и правила полуоткрытых интервалов.
- Процесс — контейнер; перенос сдвигает все задачи на тот же календарный интервал ровно один раз; растягивание задачи наружу расширяет процесс.
- Клик по процессу раскрывает его; открытых процессов может быть сколько угодно.
- Double click по названию — inline rename; handle сверху-слева для move; края для resize; Esc для отмены жеста; отдельный hover исполнителя.
- Никаких коллизий у двух задач в одной дорожке; горизонтальные отрезки на разных дорожках могут пересекаться.
- Панель свойств справа, нижняя панель занятости, кнопка выходных и существующие тесты остаются.

## 7. Не включать в эту итерацию

Нет нужды одновременно добавлять: Supabase, ChatGPT, авторизацию, онлайн, PDF, портфолио, Dexie, глобальный CommandBus, полноценный ассайнинг, multi-select/undo, создание процессов и задач. Эти задачи подробно выделены в следующем roadmap. Не делайте полумёртвые кнопки «Сохранить», «PDF» или «Добавить задачу». Не менять стек и не начинать новый проект.

## 8. Проверяемые критерии приёмки

1. **Вид 1440×900:** после загрузки демонстрации сразу узнаваемый календарный план: минимум два читаемых заголовка соседних месяцев, 6+ читаемых недельных делений в видимом окне, цветные полосы, раскрытые задачи, этапы, нижняя занятость и правая панель. Год по умолчанию НЕ умещён целиком.
2. В стартовом виде недельное деление шире 75 px; линии этой недели в шапке, производстве и занятости отличаются по X не более чем на 1 CSS px.
3. Выбор `1d`, `2d`, `3d`, `1w`, `2w`, `1mo` реально меняет вид календарной **шапки и сетки**, а не только значение выпадающего меню; не изменяет даты задач.
4. При zoom `+/-` задачи, линии этапов и полосы исполнителей масштабируются синхронно, текущие даты не меняются.
5. Pan из пустой области и средней кнопкой даёт синхронное смещение всех слоёв по X. Даты процессов/задач сохраняются.
6. Кнопка «Сегодня» выводит актуальную календарную линию в область просмотра, «Весь проект» показывает весь диапазон, а дальнейший `+` возвращает рабочую читаемость.
7. При включении выходных видны корректные бледно-зелёные полосы. При выключении они исчезают. Проверить на переходе через границу месяца.
8. По вводу новой даты этапа его разделитель перемещается на соответствующую колонку; перетаскивание маркера обратно обновляет подпись даты.
9. На 1280×800, 1440×900 и 1920×1080 календарь не содержит наложения подписей и не перекрывается правой панелью. Левый заголовочный gutter не перекрывает полосы.
10. Существующие сценарии drag/resize/expand/rename не регрессируют. Все тесты `npm run lint`, `npm run build`, `npm run test`, `npm run test:e2e` проходят — либо причина невозможности выполнения честно зафиксирована.
11. Сделать реальные **снимки браузера после изменений**: 1440×900 стартовый рабочий масштаб, 1440×900 `Весь проект`, 1920×1080 рабочий масштаб; добавить в `docs/screenshots/` и сослаться на них в отчёте. Не создавать SVG-макет и не выдавать его за снимок реально работающей страницы.
12. Документация README: честно обозначить V1.1; перечислить ещё не реализованные функции. Не менять реальное сохранение: оно по-прежнему будет отсутствовать до отдельного этапа.
