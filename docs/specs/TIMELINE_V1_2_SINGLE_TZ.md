# TIMELINE — единое ТЗ для Codex, версия V1.2

**Проект:** [messagetomedium/TIMELINE](https://github.com/messagetomedium/TIMELINE)  
**Назначение документа:** один самодостаточный файл требований для разработки следующего этапа — вкладки «Проекты» с представлениями «Карточки / Таймлайн», реальными проектами и локальным сохранением.  
**Базовый код на момент подготовки предыдущего задания:** `main`, коммит `8535428ce4d` (29 октября 2026 г.). Перед внесением изменений Codex должен проверить актуальный HEAD и адаптировать работу к новым коммитам, если они появились.

## Как использовать этот файл

1. Добавить **этот один файл** в контекст Codex (прикрепить или поместить в репозиторий, например `docs/specs/TIMELINE_V1_2_SINGLE_TZ.md`). Никаких дополнительных файлов из предыдущего комплекта V1.2 не требуется.
2. Отправить короткий промпт из сообщения ChatGPT. Codex читает **весь этот файл**, включая архитектуру, этапы и приёмку.
3. В случае противоречия с более ранними ТЗ приоритет у этого документа **по вопросам V1.2 и порядка разработки**. Существующая календарная логика V1.1 и работающие функции внутреннего редактора сохраняются.
4. Новых серверов, аккаунтов, AI-интеграции или PDF-экспорта в V1.2 нет. Эти возможности остаются в дорожной карте, приведённой в главе 4.

## Основные критерии успешного этапа

- Во вкладке **«Проекты»** переключаются две полноценные формы одного списка проектов: **Карточки / Таймлайн**. Переключателя во внутреннем редакторе нет.
- Общий таймлайн — **реальная календарная сцена с одной осью дат**, а не полосы прогресса с условной шириной.
- Можно создать пустой проект и наполнить его как минимум одним процессом и задачей; дублировать проект со всеми связями; переименовать и удалить с подтверждением.
- Проекты и их содержимое **не пропадают после F5**: используется IndexedDB с проверяемой схемой и безопасным однократным демо-заполнением.
- При перемещении проекта через отдельную ручку на портфеле всё вложенное расписание смещается на **одну и ту же** календарную дельту и сохраняется атомарно.
- Существующая временная сцена процессов/задач V1.1 остаётся рабочей.

## Глава 1. Функциональное ТЗ и сценарии интерфейса

**Продукт:** TIMELINE — визуальный редактор производственных планов.  
**База:** `messagetomedium/TIMELINE`, `main` на 29.10.2026, коммит `8535428ce4d`.  
**Приоритет требований:** этот документ переопределяет старый roadmap только в части приоритета раздела «Проекты» и локальных данных. Действующие календарные требования V1.1 и правила редактора V1 продолжают действовать.

### 1. Результат этапа, который должен увидеть пользователь

В верхней навигации есть **одна вкладка «Проекты»**. При её открытии появляется полноценный рабочий экран с переключателем **«Карточки» / «Таймлайн»**. Оба режима показывают **одни и те же реальные проекты**. В режиме таймлайна проекты нарисованы горизонтальными полосами по датам на общей календарной сетке. Нажатие на проект открывает его собственный редактор процессов и задач. При возвращении сохраняется ранее выбранный режим списка проектов.

Это НЕ два разных вида внутреннего таймлайна проекта. Внутренний редактор не должен получить переключатель «Карточки / Таймлайн».

Одновременно должны работать: новый пустой проект, глубокое копирование, переименование, безопасное удаление, локальное сохранение после перезагрузки и перенос целого проекта на общей временной оси со сдвигом всего его расписания.

### 2. Структура экранов

#### Экран «Проекты» — общая шапка

- Заголовок **«Проекты»**; рядом компактные сегментированные кнопки с иконками **«Карточки»** и **«Таймлайн»**; действующий режим визуально выделен.
- Кнопка **«+ Новый проект»** всегда доступна и в режиме карточек, и в режиме таймлайна.
- Переключатель **не должен** дублироваться внутри `TimelineWorkspace`.
- Никакой обязательной авторизации, сервера и перехода в другие приложения.
- Переключение режима происходит без перезагрузки, без потери выделения, без сброса данных.
- После входа внутрь проекта кнопка «Проекты»/«Назад к проектам» возвращает на этот экран; стрелка «Назад» браузера по возможности работает ожидаемо.

#### Режим A — «Карточки»

- Сетка адаптивных карточек: название, краткое описание (если есть), даты начала и окончания, цветовой акцент, понятный переход «Открыть».
- Никаких процентов выполнения и бесполезных KPI.
- Карточки одного проекта соответствуют ровно одной записи в локальном хранилище.
- Контекстные действия на карточке (меню «···»): **Переименовать**, **Дублировать**, **Удалить**. Удаление только после подтверждения.
- Карточки остаются полноценным альтернативным видом, их нельзя заменить мини-списком или строками таймлайна.

#### Режим B — «Таймлайн» (портфель)

Это отдельная **календарная сцена** той же визуальной семьи, что и таймлайн задач, но вместо процессов отображаются **проекты**.

- Сверху — реальная временная ось с месяцами и ячейками дней / 2 дней / 3 дней / недели / 2 недель / месяца, как в редакторе проекта.
- Слева — **неподвижная колонка с названиями проектов**; она не закрывает горизонтальные полосы. Каждая строка = один проект. Порядок строк детерминирован и не меняется из-за пересечений дат.
- Справа от фиксированной колонки — **цветная полоса проекта** на общем календаре. Её X-координата и ширина рассчитываются из настоящих дат проекта. Полосы проектов могут находиться в одних и тех же месяцах, но на разных строках.
- **Не показывать вложенные процессы/задачи в портфеле**. Это верхнеуровневое планирование. Для деталей пользователь открывает сам проект.
- Название проекта читается в колонке и/или внутри полосы (если хватает ширины). Короткая полоса не обрезает смысл: tooltip содержит полное название и даты.
- Общая линия **«Сегодня»** проходит вертикально через календарь и строки проектов. Субботы/воскресенья по кнопке подсвечиваются бледно-зелёным. Сетка и колонки действительно продолжаются вниз до последней строки.
- Панорамирование средней кнопкой мыши или ЛКМ по пустой области, zoom `+` / `−`, независимый шаг сетки/привязки. Кнопки **«Сегодня»** и **«Все проекты»**. Последняя подгоняет диапазон ВСЕХ сохранённых проектов, а не только первого.
- Стартовый масштаб: рабочий (например 14 px/день), **не** принудительно весь многолетний портфель в ширину окна. «Все проекты» — только по кнопке.
- Все горизонтальные слои портфеля (календарная шапка, полосы, линии сетки, линия сегодня) используют одну `TimelineCamera` и функцию `xForDate`.
- На каждой полосе **отдельная маленькая ручка перемещения**. Перетаскивание тела полосы НЕ меняет даты. Нажатие на полосу/название открывает внутренний редактор проекта. Различать click и drag, чтобы после переноса проект случайно не открывался.
- При переносе ручки вправо/влево весь проект смещается по выбранному шагу сетки. Во время жеста — preview и подсказка даты/сдвига; `Esc` отменяет, отпускание мыши подтверждает одну атомарную команду.
- **Не добавлять изменение длительности проекта растягиванием краёв в этом этапе.** Пока пользователь может перемещать проект целиком; правила ручного изменения его границ обсудим позднее.
- Контекстные действия «···» в фиксированной колонке: переименование, дублирование, удаление.
- Портфель показывает проекты, даже если у них ещё нет процессов/задач: пустой проект всё равно имеет явный начальный диапазон.

### 3. Действия с проектами

#### Новый проект

- Кнопка «+ Новый проект» открывает небольшую форму: **название**, необязательное описание, **начальная дата**, **конечная дата**. По умолчанию предложить диапазон от текущего месяца на несколько месяцев вперёд, но дать изменить обе даты до создания.
- Новый проект **пустой**: ни одной демо-задачи или демо-процесса. Создать только необходимые служебные данные/стартовую дорожку для редактора.
- Новый проект немедленно виден в обоих режимах «Проекты» и открывается в редакторе.
- Не показывать пользователю пустой проект как неисправный редактор: внутри него видны календарь, даты и кнопка «+ Процесс».

#### Минимальные операции для пустого проекта

- Добавить **процесс**: название, дата начала, дата конца; создать его полосу на выбранной верхней дорожке/новой дорожке, учитывая правило недопустимости перекрытия на одной дорожке.
- Добавить **задачу** внутри выбранного процесса: название, начало, окончание; строка принадлежит родительскому процессу, диапазон помещается в родителя или расширяет его.
- Элемент после создания редактируется уже существующими drag/resize/rename. Даты рассчитываются через существующую календарную модель.
- Пустая область должна содержать явные действия добавления, а не требовать скрытых горячих клавиш. Для этого этапа достаточно простых форм, не требуется полноценный будущий инспектор.

#### Дублирование проекта

- Из карточки или строки портфеля доступно «Дублировать».
- Скопировать **весь текущий документ проекта**, а не только заголовок: этапные линии, StageBand, дорожки, процессы, задачи, их связи, назначения, даты, цвета процессов, описания и сохранённое расположение/раскрытие.
- Создать новые ID для нового проекта и всех **проектных** сущностей, корректно переадресовать ссылки и развернутые ID. Внешние/global person ID сохранять или ссылочно связывать; не создавать случайные дубликаты одного человека.
- По умолчанию копия имеет те же даты и длительность, название «{исходное название} — копия». Пользователь сможет позднее переместить её на общей шкале.
- Изменение копии **никогда** не меняет оригинал.
- Не копировать встроенные файловые объекты, которых пока нет в модели; будущие вложения требуют отдельного механизма. Не выдавать частичную копию за полную.

#### Перенос всего проекта

При перемещении горизонтальной полосы в портфеле на `Δ` календарных дней должны измениться ровно на `Δ`:

1. Начало и окончание самого проекта, а также его якорная дата.
2. Даты **всех** процессов проекта.
3. Даты **всех** вложенных задач (каждая задача только один раз).
4. Даты **всех** StageMarker; StageBand остаются корректно связанными со своими маркерами.
5. Полосы занятости исполнителей в редакторе обновляются автоматически, поскольку они следуют датам назначенных работ.

Сохраняются длительности, относительные интервалы между задачами, laneId, принадлежность процесса и задачи, назначения, названия и статусы. Метаданные `createdAt` не меняются; `updatedAt` обновляется только при commit. Изменение атомарное: либо весь проект изменён и сохранён, либо ни одна дата не изменилась.

#### Переименование / удаление

- Переименование обновляет карточку, строку портфеля, шапку открытого проекта и сохранённый документ.
- Удаление только через явное подтверждение с названием проекта; удаляется именно выбранный проект, остальные не затрагиваются.
- После удаления активного проекта приложение возвращается к «Проектам» без пустого экрана или ошибочных ссылок.

### 4. Сохранение, импорт и поведение при обновлении страницы

- **IndexedDB (Dexie)**: все созданные проекты, их содержимое и текущие изменения сохраняются локально в браузере. После refresh проекта и возврата во вкладку «Проекты» всё остаётся на месте.
- Автосохранение только после подтверждённого действия; предварительные координаты во время drag не записываются по каждому pointermove.
- Оба вида «Проектов» используют один список документов из одного репозитория, а не собственные копии. При переходе между ними не пропадают проекты и правки.
- Отдельно сохранить предпочтение «Карточки/Таймлайн», масштаб/позицию камеры портфеля, шаг сетки, подсветку выходных. Это не те же prefs, что у внутреннего проекта.
- Демо «Сказки Амура» можно создать **однократно** на самом первом запуске новой локальной базы. Признак инициализации должен гарантировать, что удалённый пользователем демо-проект не восстановится снова при следующем запуске.
- Рядом с настройками хранения указать, что это **локальные данные данного браузера**, пока без синхронизации между устройствами.
- Нужны минимальные кнопки **«Экспортировать резервную копию JSON»** и **«Импортировать JSON»** для сохранения/переноса данных. JSON строго валидируется, нельзя повреждать существующие данные частичным импортом; при совпадении ID предложить импорт как копию с новыми ID или отмену.
- PDF остаётся отдельным будущим этапом, его не подменять JSON.

### 5. Ограничения и совместимость

- Сохранить текущую графическую систему, светлый интерфейс, компактные цветные полосы и реальный календарь.
- Внутренний редактор V1.1 не заменять другим Gantt-компонентом.
- Не внедрять сервер, Supabase, аккаунты, OAuth, ChatGPT и MCP в этот этап.
- Не добавлять переключатель «Карточки/Таймлайн» внутрь проекта.
- Не показывать готовые, но неработающие кнопки.
- Не обещать синхронизацию с телефоном при локальном IndexedDB.
- Достаточно desktop-first; мобильный просмотр запланирован отдельно.

### 6. Обязательные сценарии приёмки

**A. Два вида.** Открыть «Проекты» → видны реальные карточки → переключить «Таймлайн» → видны те же проекты в отдельных строках на настоящей календарной оси → снова «Карточки»: состав не меняется. При возвращении из редактора выбранный режим сохраняется.

**B. Реальные проекты.** Создать пустой проект «Проект Б» → увидеть его в обоих режимах → открыть → создать процесс и задачу → закрыть/перезагрузить страницу → оба элемента и даты сохранились.

**C. Копия.** Дублировать демо-проект с несколькими процессами, задачами и этапами → сравнить количество и связи → перенести задачу копии → оригинал не изменился → refresh сохраняет оба.

**D. Общий перенос.** Создать два проекта. Переместить «Проект Б», начинающийся на границе недельной сетки, ровно на 7 дней при недельном шаге → его проектный диапазон, каждый процесс, каждая задача и каждый маркер этапа сдвинуты ровно на 7 дней; «Проект А» не изменился. После refresh перенесённые даты остаются.

**E. Геометрия.** На масштабах день/неделя/месяц start X каждой проектной полосы совпадает с датой в шапке и линиями сетки в пределах 1 CSS px. Zoom и изменение шага сетки сами по себе никогда не меняют даты.

**F. Работа мышью.** ЛКМ на полосе открывает внутренний редактор; нажатие и перетаскивание **только ручки** сдвигает проект. Esc отменяет preview. Пустая область панорамируется. Не должно возникать случайного открытия проекта после drag.

**G. Надёжность.** Удалить проект → подтверждение → исчезает из обоих режимов. Перезагрузить → удалённый проект не восстанавливается. JSON backup/export + import проходят проверку схемы. Не допускается перезапись всех данных демо-инициализацией.

**H. Регрессия.** Внутренний редактор по-прежнему умеет pan/zoom, редактирование названий, drag/resize задач и процессов, раскрытие процессов и подсветку исполнителей. Все прежние unit/e2e тесты остаются проходящими.

### 7. Что явно НЕ входит в V1.2

- Shift-множественное выделение и вертикальный перенос существующих задач между строками.
- Полноценный инспектор, редактирование исполнителей, автодополнение имён и раскрывающиеся группы лидов.
- Полная Undo/Redo система: в V1.2 достаточно Esc для отмены жеста и подтверждения опасных действий. Историю реализуем следующим отдельным этапом на общей системе команд.

Это не отказ от ранее согласованных требований — все они остаются в roadmap.

Цель: впервые превратить V1.1 single-demo into **multi-project local application** и добавить отдельную общую временную сцену проектов. **Не переписывать существующий таймлайн редактора.**

### 2. Разделение UI

```text
App
 ├─ ProjectsPage (путь / или /projects)
 │   ├─ ProjectsHeader + ViewSwitch (CARDS | TIMELINE)
 │   ├─ ProjectCardGrid
 │   ├─ PortfolioTimeline (общая календарная камера)
```

#### Single source of truth

В `App` вместо `useState(oneDemoDocument)` нужен workspace слой, управляющий списком проектов и загрузкой активного. UI не имеет права хранить вторые независимые копии данных в карточках и портфеле.

Предложение модулей (имена не обязательны, обязанности — обязательны):

```text
src/application/workspace/
  WorkspaceService.ts           # list/create/clone/rename/delete/import/shift
  projectClone.ts               # pure deep clone с map ID
  projectShift.ts               # pure shift всех календарных дат
  createEmptyProject.ts         # pure factory
  projectCommands.ts            # serializable commands + validation
src/infrastructure/local/
  database.ts                   # Dexie, IndexedDB, versioning
  IndexedDbProjectRepository.ts
  workspacePreferences.ts       # portfolios view preference
src/features/projects/
  ProjectsPage.tsx
  ProjectCardGrid.tsx
  PortfolioTimeline.tsx
  ProjectBar.tsx
  ProjectDialog.tsx
src/features/timeline/

```

`ProjectRepository` хранит агрегаты, а `WorkspaceService` выполняет команды и валидирует их. Компоненты передают только намерение: `createProject`, `duplicateProject`, `moveProject`, `deleteProject`; не меняют Dexie напрямую.

### 3. Локальное хранилище и инициирование

#### Dexie

Минимальная структура:
- `documents`: `id`, `revision`, `updatedAt`, валидируемый `ProjectDocument` (можно хранить объект целиком). Записывать атомарно один документ на действие.
- `preferences`: ключ `portfolio`, значение `{ mode, step, zoomPxPerDay, panX, showWeekends, sort? }`, версия данных. Значения камеры не вмешиваются в проектные даты.
- `metadata`: `initialized`, `schemaVersion` для однократной инициализации.

При старте:
1. Открыть IndexedDB, выполнить миграцию версии.
2. Если metadata.initialized отсутствует — добавить **один** знакомый демо-проект «Сказки Амура» и записать `initialized=true` транзакционно. Если данных уже было больше, не перезаписывать их.
3. Загрузить список сохранённых проектов; отрисовать `ProjectsPage`.
4. При ошибке хранилища показать нормальное сообщение, не сбрасывать базу и не заменять результат демо-моделью молча.

`ProjectRepository.save(document, expectedRevision)` обязан проверять ревизию, включая создание (`null`), в том же атомарном действии. Не сохранять `pointermove`; запись только на `pointerup` или подтверждение формы. Не использовать `localStorage` как единственную базу документов (оно допустимо только для мелких UI prefs, хотя предпочтительнее Dexie).

#### JSON backup

Экспорт списка проектных документов и предпочтений через versioned JSON envelope. Импорт: read -> parse/validate -> show count + collisions -> atomic import or cancel. No partial import. При импортировании копий remap project-scoped IDs. Придерживаться текущего `ProjectDocument` schema validation; не принимать произвольный JSON как готовый объект UI.

#### Персоналии

Текущая схема хранит `people` внутри `ProjectDocument`; глобальный каталог людей в окончательной архитектуре появится на этапе полного редактора исполнителей. В V1.2 не дублировать личность при копировании проекта: ID людей можно сохранить с согласованной семантикой, но не реализовывать фиктивную «глобальную синхронизацию карточек». Задокументировать переход к глобальной таблице при следующей миграции. Новым пустым проектам допускается пустой `people`.

### 4. Модель портфеля

Портфель — **проекция** нескольких сохранённых ProjectDocument. Он не является отдельным файлом с копиями процессов и не владеет собственными задачами.

`PortfolioProjectRow` (computed):
- `projectId`, `name`, `sortIndex`, `range`, `color`, `snapshotRevision`.
- `range` = объединение явно заданных `project.startDate`, `project.endDateExclusive`, интервалов процессов, задач и StageMarker (для включения маркера используйте `addDays(marker.date, 1)` в end-exclusive). Пустой проект использует проектный диапазон.
- `color`: детерминированная мягкая палитра по стабильному ID проекта. В V1.2 не расширять текущую схему без нужды только ради выбора цвета. Все представления одного проекта показывают одинаковый акцент.

`PortfolioViewPrefs` живёт **отдельно** от `document.viewPreferences`, чтобы изменение масштаба/шага портфеля не меняло масштаб внутреннего проекта. Если пользователь переключает карточки/таймлайн, не выбрасывать `PortfolioViewPrefs`.

#### Геометрия

- `.projects-page` занимает доступную ширину браузера, не ограничивается старым `main { width:min(1120px,90vw) }`.
- Фиксированный gutter для имён проектов, временной viewport отдельной измеряемой ширины; CSS grid/DOM позиционирование как в V1.1, не накладывающаяся поверх полос шторка.
- Один `TimelineCamera` для ruler + grid + project bars + today line. Горизонтальное панорамирование/zoom при изменении ширины viewport сохраняет текущую точку, не вызывает auto-fit.
- Строка проекта имеет фиксированную комфортную высоту; последовательность из sortIndex и ID, независимо от пересечений. Для большого списка допустима вертикальная прокрутка и виртуализация **после** проверки реальной потребности.
- Подсветка weekend и сетки — те же `CalendarCell`, что в индивидуальной сцене. Открытие проекта — навигация по click, отдельная ручка проекта — pointermove.

### 5. Атомарные доменные операции

#### ShiftProject(projectId, deltaDays)

Чистая функция, не зависящая от React/Dexie:

```ts
shiftProject(document: ProjectDocument, deltaDays: number): ProjectDocument
```

Требования:
- Сдвинуть `project.anchorDate`, `project.startDate`, `project.endDateExclusive`.
- Сдвинуть каждый `stageMarker.date`, `process.start/end`, `task.start/end` **по одному разу**.
- `stageBand.leftBoundaryId/rightBoundaryId` не менять — маркеры остаются теми же сущностями.
- Не сдвигать даты чужих проектов, создавать/обновлять revision последовательно, `createdAt` не менять.
- Не трогать lane, assignments, person IDs, titles, statuses, colors, descriptions.
- Получившийся документ пропустить через `projectDocumentSchema.safeParse` **до сохранения**.
- Один `ProjectRepository.save` на команду с expected revision. При конфликте показать ошибку и загрузить актуальное состояние, не перезаписывая молча.
- `Esc`, `pointercancel` и ошибка валидации => никакой записи.

На недельной сетке перенос выполняется через `snapDate`, но должен вычислять *один общий deltaDays*, который затем применяется ко ВСЕМ дочерним элементам. Следить, чтобы при Shift всей сущности вы не снаппили каждую задачу по отдельности (это ломает относительные интервалы).

#### DeepCloneProject(source)

Сделать карты ID старый->новый для `project`, `stageMarker`, `stageBand`, `lane`, `process`, `task`, `assignment`. Переназначить все `projectId`, `processId`, `laneId`, `targetId`, boundary references, view prefs expansion IDs. `personId` пока сохранять как одну идентичность. Все объекты нового документа должны быть собственными, без shared mutable references; использовать чистые функции и уникальные IDs.

Имена, даты, длительности, цвета процессов, назначения и порядок строк наследуются. Изменение копии не меняет источник. Назначить новый `createdAt`, `updatedAt`, revision как для нового документа. Валидировать.

#### CreateEmptyProject

Создать проект с явным диапазоном дат, пустыми `stageMarkers`, `stageBands`, `processes`, `tasks`, `assignments`, `people`, с одной верхней process lane и стартовыми `viewPreferences`. Никакого автоматического набора демо-элементов.

#### CreateProcess / CreateTask

Простые application commands. Они проверяют даты, принадлежность дорожке, пересечения на одной дорожке и containment. Для новой задачи подобрать или создать подходящую дочернюю дорожку; **не** проводить произвольную автоматическую «упаковку» уже существующих задач. Если нужно расширить родителя, делается той же атомарной командой. Эти операции нужны, чтобы новый проект не был пустой мёртвой оболочкой.

### 6. Навигация / состояние

- `ProjectsPage` имеет режим `cards|timeline`, сохраняемый среди workspace prefs.
- Внутренний `ProjectEditorPage` получает `projectId`, загружает документ из repository и отдаёт обновления общему WorkspaceService.
- Если из карточки/полосы открывается тот же ID, должен открываться тот же документ и история изменений, а не созданная копия демо.
- При удалении проекта, который был открыт, не продолжать показывать устаревший документ. Предусмотреть loading/error/empty состояния.
- Browser back должен возвращать из `/projects/:id` на `/projects` там, где это технически возможно; для этого можно использовать React Router или корректный History API. Нельзя вводить авторизацию ради навигации.

### 7. Future-safe архитектура, но без реализации сервера

Запись через `WorkspaceService` и чистые сериализуемые commands — будущая точка входа для Supabase и ChatGPT MCP. Не создавать сейчас сетевые API. В будущем:
- серверные транзакции выполнят те же доменные правила;
- optimistic revisions + права ролей;
- предварительное подтверждение AI-пакетов изменений;
- guest links ограничены конкретным проектом.

### 8. Проверки

Unit: глубокое копирование ID/ссылок, ShiftProject, реальный месяц, DST, пустой проект, сохранение относительных интервалов, схема, запрет чужой mutation, revision conflict.  
Integration: Dexie save/load/list/delete, отсутствие повторного seed, batch import, reload.  
Playwright: оба режима/переключение, создание двух проектов, clone, move via dedicated handle, fit all, панорамирование, детерминированная календарная геометрия, reload, возврат в проект, old V1.1 regressions.  
Screenshots: 1440×900 (cards), 1440×900 (portfolio), 1440×900 (inner editor), 1920×1080 (portfolio).  

Все тесты должны проверять реальное поведение, а не только наличие компонентов. Не обновлять reference screenshots автоматически с ложными проходами без сравнения.

## Глава 3. Порядок реализации для Codex

Работать **в существующем** репозитории `messagetomedium/TIMELINE`. Не переносить код в новый проект. Приоритет — получить законченную продуктовую функцию «Проекты: карточки / таймлайн», а не ещё один абстрактный каркас. В любой промежуточной версии страница «Проекты» должна запускаться.

### Этап 0. Проверка перед изменениями

- Вывести HEAD, проверить `src/app/App.tsx`, `ProjectOverview.tsx`, `TimelineWorkspace.tsx`, `ProjectRepository.ts`, схемы и CI.
- Запустить исходные `npm run lint`, `npm run build`, `npm run test`, `npm run test:e2e` в доступном окружении; зафиксировать результаты (не скрывать отказ браузера/зависимостей).
- Создать отдельную ветку `feat/projects-portfolio-v1-2` из актуальной main. Не удалять пользовательские файлы.

### Этап 1. Сквозной видимый вертикальный срез (ОБЯЗАТЕЛЬНЫЙ)

- Заменить `App` с одним демо-документом на `ProjectsPage` с несколькими проектами и активным ID.
- Подключить настоящий IndexedDB/Dexie repository, однократный seed демо, loading и error states.
- **Сразу** вывести переключатель **«Карточки / Таймлайн»**. В режиме таймлайна уже должен быть календарный ruler, сетка и полосы проектов — не откладывать визуальную часть после создания десятка абстрактных сервисов.
- Показать, что оба режима читают один источник данных и что выбранный режим переживает перезагрузку.

**Контрольный просмотр:** после нажатия «Проекты» можно переключить карточку в календарный портфель и обратно, а экран в масштабе рабочего времени читабелен. Если только карточки — этап не завершён.

### Этап 2. Создание и копирование

- «+ Новый проект»: диалог, пустой валидный документ, запись в IndexedDB, открытие редактора.
- В пустом редакторе простые работающие «+ Процесс» и «+ Задача», иначе «Новый проект» является бесполезной заглушкой.
- «Дублировать»: чистая глубокая копия всех проектных вложенных сущностей с переразметкой всех внутренних ID и проверкой схемы.
- Переименование и удаление с подтверждением.
- Обновить обе формы представления после каждой команды без reload.

**Контрольный просмотр:** создать проект Б, добавить процесс и задачу, сделать копию проекта А, вернуться в карточки/портфель, затем перезагрузить страницу — содержимое осталось.

### Этап 3. Перенос проекта в общем таймлайне

- ProjectBar: отдельная ручка drag, preview, snap и атомарный `ShiftProject`.
- Родительский проект и все его descendants сдвигаются **одинаковым** `deltaDays`. StageBands сохраняют связи.
- Обычный click проекта открывает внутренний редактор. Drag handle не вызывает click/open; отмена Esc не сохраняет изменений.
- При любых коллизиях или ошибках range должен быть понятный отказ; соседние проекты НЕ блокируют перенос (каждый на отдельной строке).

**Контрольный просмотр:** после перемещения проекта Б на 7 дней откройте его — сдвинуты все вложенные полосы/этапы. Проект А остался на месте.

### Этап 4. Бэкапы и полировка

- Экспорт/импорт JSON, валидируемая схема и сообщение при конфликтах. Не маскировать под экспорт PDF.
- Портфель: today/fit/zoom/grid/weekend, явная пустая область, длинные имена, компактные/далёкие полосы, адаптация размеров экрана.
- Состояния loading, no projects, storage error, missing project ID, deletion.
- Правки не должны теряться при переходе из портфеля во внутренний редактор и назад.

### Этап 5. Проверка и публикация

- `npm run lint`, `npm run build`, `npm run test`, `npm run test:e2e` — все реально выполнить и привести результаты; исправить регрессии V1.1.

### Definition of Done

Задание считается выполненным **только если одновременно**:

1. «Проекты» имеют два действительно работающих вида.
2. Режим таймлайна является календарной сценой с отдельной полосой каждого проекта и рабочими zoom/pan/today/fit.
3. Проекты реально создаются, копируются, удаляются и сохраняются после refresh.
4. Пустой проект можно наполнить хотя бы одним процессом и задачей.
5. Перенос проекта на портфеле атомарно изменяет все даты его содержимого.
6. Внутренний V1.1 не сломан, проходят исходные тесты.

Не принимать страницу только с двумя декоративными кнопками, одну демо-карточку, ненастоящие CSS-полосы, а также «реализацию» из README без рабочего интерфейса.

### V1.5 — экспорт

- PDF текущего **настроенного вида** (масштаб/видимость/раскрытие/цвета/порядок строк, включая нижнюю шкалу людей, если показана).
- Корректная печать длинного диапазона на одной настраиваемой странице без обрезания данных. Отличать full scene vs viewport capture; уточнить формат на визуальной приёмке.

### V2.0 — многопользовательская система

- Supabase/PostgreSQL, email+пароль и Google OAuth, серверные RLS/права, admin и read-only guest по ссылке только на назначенный проект.
- 5–20 пользователей, presence, краткосрочная блокировка редактируемой сущности, атомарные команды и конфликты ревизий, realtime.
- Импорт локальных проектов на сервер с проверкой сохранности и ссылок.
- Мобильный интерфейс просмотра и изменения статусов.

### V2.1 — ChatGPT

- Собственный защищённый MCP: читать проекты, искать/анализировать, формировать план, назначать исполнителей, предлагать изменение дат.
- Draft -> diff preview -> явное подтверждение пользователя -> atomic commit.
- Права доступа ограничены правами соответствующего пользователя; никакого «полного безграничного database key» внутри ChatGPT.

### Ключевое правило

Каждый этап закрывается проверяемыми действиями в браузере, рабочей сборкой и e2e. Не заменять реальный UX новыми необязательными архитектурными абстракциями.

## Глава 5. Контракт для Codex: что считать сдачей V1.2

1. Работать **только в существующем** `messagetomedium/TIMELINE`; прочитать текущий код и этот документ до реализации. Не заменять V1.1 новой библиотекой Gantt, не создавать второй источник истины для проектов.
2. До начала изменений зафиксировать базовый HEAD, результаты исходных тестов и состав затрагиваемых модулей. Создать рабочую ветку; не удалять/сбрасывать пользовательские данные и текущую историю коммитов.
3. Сначала добиться **видимого рабочего экрана «Проекты»** с переключаемыми карточками/таймлайном; не заканчивать этап, реализовав только схемы и интерфейсы.
4. Для всех пользовательских действий использовать проверяемые команды/сервис, а не прямые записи из React-компонентов в IndexedDB. Для жестов: preview до pointerup, атомарная запись после подтверждения, Esc отменяет.
5. Демонстрационный проект допускается один раз при первой инициализации пустой локальной БД. Впоследствии удалённый демо-проект нельзя восстановить автоматически.
6. Проверить в настоящем браузере: оба вида, создание/копирование/удаление, перенос на 7 дней и неизменность другого проекта, сохранение после F5, работу существующего индивидуального редактора.
7. Выполнить `npm run lint`, `npm run build`, `npm run test`, `npm run test:e2e`. Не скрывать непрошедшие проверки или невозможность запустить браузер. Сохранить реальные скриншоты интерфейса и обновить README.
8. Отчитаться по фактически выполненному: что работает, что не работает, перечень изменённых файлов, проверенный commit SHA, результаты тестов и ссылка на опубликованную версию **только если публикация действительно подтверждена**.

**Не принимать V1.2**, если «Проекты» показывают лишь одну демо-карточку, если «Таймлайн» — фальшивые CSS-полоски без дат, если нельзя заполнить пустой проект процессом/задачей, если перенос не сдвигает всех детей или если изменения исчезают после обновления страницы.
